Key Data Flows
Как данные текут через систему от звонка до UI
Recording: CoreAudio → system.wav + mic.wav
Transcription: WAV files → mlx_whisper → {text, segments[]}
Resolution: segments → Ollama qwen3:14b → speaker_map{}
Summary: transcript → Ollama + template → summary JSON
Commitments: resolved transcript → Ollama dual-prompt → commitments[]
Storage: all results → SQLite (calls.db) → SwiftUI reads
IPC: daemon writes → status.json → DaemonMonitor reads
Settings: SettingsSync writes → settings.json → settings.py reads
Processing Pipeline
6 стадий обработки звонка. Каждая стадия gated by user settings и Ollama availability.
👁
Detection detector.py
Каждые 3 сек (POLL_INTERVAL) проверяет: запущен ли процесс звонка + есть ли UDP connections. Zoom: только процесс CptHost. Остальные: процесс + ≥2 remote UDP IPs. Gated by is_app_enabled(app_name).
psutil.process_iter() net_connections(UDP) (bool, app_name)

🔴
Recording recorder.py → swift/AudioCapture
Запускает Swift subprocess (ScreenCaptureKit + AVAudioEngine). Пишет два WAV: system.wav (loopback — собеседник) и mic.wav (микрофон — я). Session ID = timestamp-based UUID. Gated by auto_record_calls setting.
CoreAudio streams system.wav mic.wav session metadata
📝
Transcription transcriber.py
Dual-channel transcription через mlx_whisper (Apple Silicon native). system.wav → SPEAKER_OTHER segments, mic.wav → SPEAKER_ME segments. Merge by timestamp в unified timeline. Gated by should_transcribe().
system.wav + mic.wav {text, segments[]} fallback: combined.wav
Формат сегментов ▾
{ "text": "Full transcript...", "segments": [ {"start": 0.0, "end": 5.2, "text": "Привет, как дела?", "speaker": "SPEAKER_ME"}, {"start": 5.5, "end": 12.1, "text": "Всё хорошо, давай обсудим проект.", "speaker": "SPEAKER_OTHER"} ] }

Model: mlx-community/whisper-large-v3-mlx | Language: ru | Rate: 16kHz mono

👤
Speaker Resolution speaker_resolver.py
Ollama определяет реальные имена из контекста разговора. 5 уровней confidence: self-intro (0.95) → direct address + response (0.85) → direct address (0.70) → third-person intro (0.65) → contextual (0.40). Requires: Ollama available + dual-channel segments.
unified_segments[] speaker_map{} skip if Ollama offline
Формат speaker_map ▾
{ "SPEAKER_ME": {"confirmed": true, "source": "mic_channel"}, "SPEAKER_OTHER_1": { "name": "Elena", "confidence": 0.85, "source": "direct_address_confirmed", "evidence": "Elena, can you send the proposal?" } }

Temperature: 0.1 | Max tokens: 2048 | Timeout: 120s

📋
Summarization summarizer.py + templates.py
Template-based summarization через Ollama. 6 шаблонов (default, sales, 1-on-1, standup, interview, brainstorm). Chunked map-reduce для длинных транскриптов (>25K chars). Entity extraction как побочный эффект. Gated by should_summarize().
transcript + template summary JSON entities[] JSON repair if truncated

🤝
Commitment Extraction commitment_extractor.py
Dual-prompt система: Karpathy (primary) + Murati (fallback). Speaker-resolved transcript как input. Chunked processing с dedup по границам. Русская специфика: перфективный вид ("сделаю") = commitment, "постараюсь" = weak. Gated by should_extract_commitments().
resolved transcript + speaker_map commitments[] extraction_notes skip if Ollama offline
Формат commitment ▾
{ "id": 1, "type": "outgoing", // outgoing | incoming | third_party "who": "SPEAKER_ME", "who_name": null, "to_whom": "SPEAKER_OTHER", "to_whom_name": "Elena", "what": "Send the revised proposal", "deadline": "к пятнице", "quote": "я пришлю тебе предложение до пятницы", "timestamp": "00:03:42", "uncertain": false }

Chunks: 25K chars, 2K overlap | Dedup: by (what, who, to_whom)

Error Handling & Graceful Degradation
Pipeline никогда не крашится. Каждый сбой → fallback → продолжение работы.
🔴 Ollama unavailable
→check_ollama() returns False
→Recording + Transcription proceed normally
→SKIP: speaker resolution, summarization, commitments
→Save call with transcript only (no AI analysis)
→status.json: ollama_available=false → UI shows warning
🟡 Separate-channel transcription fails
→Try: transcribe_separate(system.wav, mic.wav)
→Failure (mic not captured, etc.)
→Fallback: ffmpeg merge → transcribe(combined.wav)
→Transcript without speaker labels
→If merge also fails → save call without transcript
🟡 Summarization JSON parse failure
→Try: json.loads(response)
→JSONDecodeError (truncated output)
→Try: _try_repair_json() — close braces
→If repaired → use partial summary
→If unrepairable → save raw text as summary
🟡 Commitment extraction fails
→Try: Karpathy prompt
→Empty or invalid output
→Try: Murati prompt (fallback)
→If either succeeds → save commitments
→If both fail → save call without commitments (0 rows)
🔴 Token budget exhaustion (51K problem)
→Long transcript (>30K tokens) + thinking mode
→qwen3:14b spends all num_predict on thinking, 0 content
→Chunked processing splits into 25K-char chunks
→Each chunk fits within token budget
→Legacy resummarize.py has num_predict=1024 — still fails
🟢 Short call (<30s)
→Recording completes, duration checked
→Skip entire pipeline — log "too short"
→Delete WAV files, no DB insert
🟢 Pipeline crash (any unhandled exception)
→try/except around process_recording()
→Log full traceback to daemon.log
→macOS notification: "Processing failed"
→Daemon continues running, returns to IDLE state
